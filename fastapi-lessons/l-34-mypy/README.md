# Проверка статической типизации при помощи mypy

Помимо уже известных по прошлым урокам способам проверок, 
часто используют еще проверку статической типизации кода.
Если переменным, функциям итд. явно указывать типы, 
мы сможем проверять совпадают ли типы при присвоениях значений к переменным.

Проверка статических типов также помогает снижать количество потенциальных багов 
(особенно при командной разработке больших проектов).
Конечно тесты могут помочь выявить сильно больше багов, 
однако они требуют существенного времени для написания,
а проверка статической типизации автоматическая
(не отменяет того, что тесты тоже необходимы, чтобы не спотыкаться на стадии поддержки проекта!).
Ну и бонусом твоя IDE будет больше тебе помогать, если код проекта хорошо типизирован.

На данный момент самый популярный инструмент для проверки типизации кода - **mypy**.

Установим его как зависимость для тестов:
```shell
poetry add mypy --group test
```

Запустить проверку конкретного модуля проекта (например **src**) можно при помощи команды:
```shell
poetry run mypy src
```

По началу он будет выдавать очень много ошибок.

Чтобы по началу получать ошибки mypy не во всех ситуациях, 
а только в тех, где это наиболее необходимо в проекте, 
можно задать настройки его поведения в **pyproject.toml**:
```toml
[tool.mypy]
python_version = "3.10"
cache_dir = ".mypy_cache"
strict = true
warn_return_any = true
warn_unused_configs = true
disallow_untyped_defs = true
disallow_incomplete_defs = true
check_untyped_defs = true
disallow_subclassing_any = true
disallow_untyped_decorators = true
```
Здесь mypy будет ругаться на почти любые несоответствия типов.
Ты же можешь выбрать менее жесткую конфигурацию 
(особенно, если прикручиваешь mypy к уже существующему большому проекту).

Также для начала можно использовать заглушки в виде типов `Union`, `Optional`, `Any`.
Новый код же или какие-то критические модули лучше сразу типизировать полноценно. 

Порой чтобы mypy нормально работал со сторонними пакетами, 
нужно указывать дополнительные плагины для него.
Так, для работы с `sqlalchemy` 
необходимо добавить также настройку использования специального плагина 
(stub-плагины для работы с библиотеками без типов):
```toml
[[tool.mypy.plugins]]
name = "sqlalchemy.ext.mypy.plugin"  # for SQLAlchemy
```

Также (ну собственно и во всех других QA библиотеках) 
можно отключать какие-то проверки на конкретные файлы.
Так например в этом проекте в **src/repository/helicopter.py** 
игнорируется проверка типизации вывода функции, 
чтобы не было проблем с override-ом выводимых значений родительского класса ```SQLAlchemyRepository```:
```python
# mypy: disable-error-code=return-value
```

Естественно mypy можно и нужно использовать с другими библиотеками для проверки кода 
(например линтерами вроде flake8 или ruff).
Также mypy проверки тоже можно смело добавлять в CI.

Более подробно о функционале библиотеки mypy (первой мажорной версии) можно почитать тут:
https://mypy.readthedocs.io/en/stable/index.html.
