# Все, что нужно знать, чтобы развернуть все web приложение локально

Почему разработчику нужно уметь запускать и фронт и бэк локально?
Даже в командах, где роли четко распределены на фронтендеров и бэкендеров, 
разработчики должны уметь проверить не ломают ли внесенные ими изменения остальные части системы.

Ты гарантированно столкнешься с необходимостью запустить какой-то кусок web приложения (будь то бэк или фронт) на работе.
Порой в больших компаниях разработчикам выделают общий демо сервер с развернутыми кусками приложения, чтобы не разворачивать это все самому 
(порой даже под каждого разработчика).
Однако в мамленьких компаниях зачастую это не так, поэтому тебе нужно понимать хотя бы общую концепцию локального запуска фронтенд и бэкенд приложений.

Особенности же запуска конкретных приложений принято описывать в документации к проекту. 
Хотя в работе порой ты будешь сталкиваться с проектами, в которых людям было лень написать документацию, в таком случае удачи тебе 
(если серьезно, то тогда придется искать людей, которые этим занимались, и предлагать дописать документацию, чтобы она была более понятной).

## Общие принципы разработки больших проектов

В современном мире существует настолько много технологий, библиотек, компонентов итд., которые используются в веб разработке. 
Поэтому при разработке больших проектов разработчики все время переиспользуют ккакие-то готовые куски кода. 
Чтобы было удобнее переиспользовать код люди в один момент начали оборачивать код, который планируется переиспользовать, в **библиотеки**. 

Библиотеки, которые можно скачать откуда-то из интернета еще часто назвают **пакетами**.

В настоящий момент почти для каждого языка существуют сервисы, 
в которых хранится большое количество пакетов для упрощения разработки приложений приложений.

Например для фронтенда (js, ts, html, css) самый популярный сервис для хранения пакетов: https://www.npmjs.com/.

Для разработки любых приложений на python: https://pypi.org/.

На подобных сайтах ты можешь найти нужные тебе библиотеки и использовать их в своих проектах с помощью пакетных мэнеджеров.
В дальнейшем ты и сам сможешь делать свои библиотеки и выкладывать их в подобные хранилища пакетов, 
чтобы другие люды могли переиспользовать твой код.

**Пакетный менеджер** - программа, с помощью которой можно удобно установить все необходимые для проекта пакеты нужных версий.

Зачастую зависимости проекта (пакеты, необходимые для его запуска) храняться либо в одной конкретной общыей папке на компьютере, либо в специальной папке внутри проекта.


## Frontend

Frontend локально разработчики обычно запускает с помощью **npm** (node package manager) и **node** (node.js).
**Npm** - менеджер зависимостей для вашего проекта (фронтенд библиотек, которые тот использует, чтобы работать).
**Node** - окружение для запуска JavaScript кода.

Разные проекты используют разные версии **npm** и **node**, поэтому чтобы менять их на ходу frontend разработчики в последнее время используют еще одну программу **nvm**.

Таким образом для того, чтобы запускать фронтенд приложения необходимо установить **nvm** (гугли, как сделать это на твоей платформе).
Потом с помощью **nvm** установить **npm** и **node** одной командой:
```shell
nvm install необходимый_номер_версии_node
```

Дальше найди в проекте папку, в которой лежит файл **package.json**. 
В нем описаны зависимости проекта и часть его настроек.
Находясь в этой папке можно установить зависимости командой:
```shell
npm i
```
Теперь можешь запускать проект. 
Разработчики могут менять команду с помощью которой запускается проект 
(в таком случае это стоит указать в README.md файле, чтобы другим было понятнее).
По умолчанию же для локального запускать используется команда:
```shell
npm run dev
```

## Backend (python)

Для питона в настоящий момент существует множество пакетных менеджеров и нет какого-то одного единого.
Наиболее популярныйе из них на 2025-й год:
- **poetry** - пока большая часть проектов конфигурируются им.
- **uv** - переосмысление poetry, немного быстрее, стремительно набирает популярность.
- **pipenv** - самый простой способ, самый старый, но менее удобный, чем выше перечисленные. 
Он уже почти полностью отошел на второй план, но порой встречается в старых проектах.
- **pip**, **virtualenv** - так уже никто не делает, 
но в совсем старых и простых проектах люди скачивали библиоти из списка библиотек, лежащих в **requirements.txt**.

Для начала вам нужно скачать версию питона, которая требуется для вашего проекта.
В настоящий мемент 2-я версия питона уже почти нигде не встречается, а у 3-й версии есть много минорных версий.
Вот страница с информацией о текущих версиях питона: https://www.python.org/downloads/.

Если используешь **uv**, можешь с помощью него же скачать нужную версию питона. 
Если другой пакетный менеждер, для начала скачай нужную версию питона, а сам потом пакетный менеджер.

Для **poetry**, **uv** и всех прочих современных пакетных менеджеров зависимости описываются в специальном файле **pyproject.toml**.
Для **pipenv** список зависимостей описывается в **Pipfile**.

Порой для упрощения использования пакетных менеджеров используют **make** для хранения команд запуска бэкенда и всего, что с ним связано.

Способы запуска приложений на бэкенде могут сильно отличаться от проекта к проекту, 
так что в случае конкретного проекта скорее всего придется читать его документацию.

### Базы данных и прочее необходимые для запуска backend

Чтобы не устанавливать и не запускать для каждого проекта свою базу данных, 
для разработчика легче всего запускать их локально в docker контейнерах.
В ходе курса ты сможешь более подробно ознакомиться с работой с докером, 
как создавать свои образы контейнеров и переиспользовать чужие.

Для начала можешь себе представлять docker контейнер как изолированную коробку, 
с которой ты сможешь легко взаимодействовать извне и которую можно развернуть из docker образа.
Docker образ же (docker image) можно собрать локально или выкачать из специальных хранилищей docker образов 
(вот самый популярный: https://hub.docker.com/).

Обычно в **README.md** файле к бэкенду в проекте разработчики оставляют описание как запускать необходимые компоненты локально.

## Запуск всего проекта целиком через docker-compose

Порой в больших проектах с большим количеством модулей для более удобного запуска 
devops инженеры делают **docker-compose.yml** файлы, с помощь которых можно разом запустить весь проект.
Для этого надо в папке с **docker-compose.yml** фалом запустить:
```shell
docker compose up -d
```

В большинстве репозиториев школы существует такая опция запуска.
